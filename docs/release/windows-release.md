## Trigger and job model

`.github/workflows/windows-release.yml` runs for every branch push and `workflow_dispatch`. A branch filter excludes tag-only events, so the release tag created by the job cannot trigger another release run.

The workflow has one `windows_release` job on the pinned `windows-2025` GitHub-hosted runner. It has `actions: read` to read the current job start time and `contents: write` to create the release. There is no concurrency cancellation: publication is a side effect, and an older qualifying run must not be cancelled by a newer push.

The token chain is `RELEASE_TOKEN`, then the organization token, then the workflow token. Tokens are passed only through `GH_TOKEN` and are never printed or copied into release evidence.

## Build and package sequence

1. Check out the exact commit with full history.
2. Install Node.js from `.node-version` and record the Actions job's `started_at` value.
3. Run the committed line counter before a build can touch generated tracked files.
4. Run `build.bat /s` to build both runnable applications.
5. Run `build-installer.bat /s` to produce and validate both installer families.
6. Resolve an unused public dim-sum code name, or record an honest catalog-unavailable reason.
7. Assemble only the allowlisted release assets and evidence.
8. Prove both installer families carry the unique `1.<run-number>.<run-attempt>` package version, create one unique non-draft release, finalize server-derived timing, download every asset, and compare hashes.
9. Under `if: always()`, collect and upload safe outputs even when an earlier build, package, or publication step fails.

The workflow runs no tests or lint. Build, packaging, unsigned-state, provenance, manifest, and release-record validation are delivery operations rather than code-quality gates.

## Version and provenance

The WPF installer name contains the full source commit. The Exchange package uses `1.<run_number>.<run_attempt>` inside a temporary package copy, leaving tracked `package.json` and `package-lock.json` unchanged. The isolated output records both the exact source commit and package version before it is admitted to release staging.

Tags use the workflow run number, attempt, and short commit. The publisher refuses an existing tag or release and never overwrites an earlier release.

## Timing

The first job step reads the current Actions job's server `started_at` value. After the non-draft release is created, the publisher reads its server `published_at` value. Release notes state both UTC timestamps and the invariant `HH:mm:ss` interval between them. A local wall-clock estimate is never substituted.

## Unsigned boundary

Code signing is permanently disabled. The Electron manifest's three signing controls remain false, certificate environment inputs are cleared, certificate auto-discovery is false, and package logs are rejected if they report `signtool`, a signer, or certificate discovery. The WPF setup, Exchange setup, and unpacked Exchange executable are parsed directly; any nonempty PE certificate table fails packaging.

Release notes warn that unknown-publisher and SmartScreen messages are expected. HTTPS transport, `RELEASES`, package hashes, and the release SHA-256 manifest provide transport and corruption evidence; they do not claim publisher authenticity.

## Failure evidence and security

The always-on collector copies only explicit generated evidence, installers, update packages, and the Exchange package log. It never uploads source trees, dependency directories, caches, credentials, environment dumps, or the Exchange ISO. Artifact upload uses a bounded retention period and cannot mask the original build failure or turn it green.

## Large media and dim sum

The Exchange ISO remains behind the repository's Cheap LFS pointer/side-asset route. The release workflow does not hydrate or attach it and never invokes standard Git LFS. The separately owned pointer verifier must prove the compressed part inventory before runtime download work can be called complete.

Dim-sum release decoration comes only from the public catalog. The workflow seeds its catalog scan from the unique workflow run number so concurrent runs begin at different dishes, then rejects every name already present in project release history and confirms the selected `catalog-v1*` photo URL. It links the photo in release notes without downloading or attaching a copy. If no unused published photo can be resolved, the release ships without a code name.

## Documentation-site build route

The documentation site has a separate build-only route at `docs-site/build.bat /ci`. It restores the site's locked dependencies, builds the Cloudflare Worker-compatible Sites output at `docs-site/dist`, and exports the same site for GitHub Pages at `docs-site/pages-dist` with the `/Windows-Server-Setupper/` base path. The `/ci` (or `--no-tests`) mode intentionally skips only the site's focused `node --test` step.

The current public deployment is https://cafepromenade.github.io/Windows-Server-Setupper/. The owner-only Sites deployment is https://windows-server-setupper-guides.labapig.chatgpt.site. The build route alone never proves a future deployment; each later publication must still upload the matching output and verify its live URL.

## Verification and failure modes

- Missing/corrupt Squirrel files fail `scripts/test-release-assets.ps1` and the real package verifier.
- Missing workflow triggers, runner, publication proof, or failure collection fail `scripts/validate-release-contract.ps1`.
- A build can stop because a canonical dependency cannot be obtained; the script reports the dependency and attempted source.
- A packaging log that indicates signing fails even if the packager exits zero.
- A release that is draft, prerelease, targets the wrong commit, misses an asset, or cannot be downloaded fails the job.
- Publication can be externally blocked by account-level GitHub Actions restrictions even when repository Actions are enabled. That is not a successful or failed application build until a job actually runs.
